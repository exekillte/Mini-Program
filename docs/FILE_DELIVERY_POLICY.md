# ChatGPT 文件交付与 GitHub 版本管理规范

> 适用范围：本仓库的程序、脚本及可公开的通用配置。它不是 ChatGPT 账号级自动设置，也不授予跨对话的 GitHub 写入权限。

## 核心规则

1. **同一产品固定路径**：一个程序保留唯一正式发布路径和文件名，不使用 `v2-final-new` 作为长期发布文件名。路径、文件名优先 ASCII；中文名称只在说明中出现。
2. **最新版覆盖内容，历史交给 Git**：每次验证成功后更新同一路径，在 `main` 留下新的 commit；Git 历史保存旧版本。不要额外堆放每一版的完整副本，除非明确要求不可变发布快照。
3. **下载入口稳定**：程序目录 README 和 catalog.json 始终指向正式路径的 `main` 版本（可用 GitHub raw 地址）。不要向用户提供过期版本的沙盒链接作为长期入口。浏览器缓存可能造成短暂更新延迟。
4. **修改前必须读取仓库最新状态**：查找程序、读取文件与 blob SHA、检查最近版本；避免把用户在其他设备做过的更新覆盖掉。同一个程序更新冲突时停止并说明，不能强行覆盖。
5. **源代码与可用文件一致**：若交付物由构建生成，可保留源码和构建产物；须验证生成物可用，并明确哪个是用户实际下载的正式文件。
6. **实际成功才宣称已备份**：GitHub 写入成功后回读文件，核验内容或版本、路径、下载地址；失败则提供当前会话可验证的文件并报告“GitHub 备份未完成”。不伪造提交、文件、链接。
7. **更新入口同步**：更新脚本版本元数据（如 `@version`）、必要文档、变更说明和 catalog.json。维护 README 里的常用工具直达链接。
8. **自动更新与自动安装不等价**：GitHub Raw 固定地址只保证后续读取最新文件；用户脚本还须 Tampermonkey 的更新检查，其他程序需各自的安装或部署机制。远程删除目录项不会自动卸载其他设备的程序。

## 发布流程（在具备可用工具和权限的对话中尽量自动执行）

- 第一步：判断是否为已有项目的修改，查找 catalog.json 及目标程序正式路径；没有则建立合理的稳定路径。
- 第二步：读取当前仓库版本；生成/修改文件；运行适用的语法、结构、输出完整性测试。
- 第三步：上传 GitHub：文本文件按 SHA 更新（或创建）；二进制文件使用确实受支持的 GitHub 上传能力。文件过大或工具不支持时，不声称已备份。
- 第四步：确认 commit、回读提交的文件，对照内容校验；更新 catalog.json 和必要的 README 说明。
- 第五步：提供**最新版固定链接**，说明版本、测试结果和 GitHub 同步状态；历史版本通过 History/Commits 查看。

## 内容安全与仓库选择

- **本仓库是 Public。** 仅默认提交可以公开的代码、通用脚本、去敏配置和无私人内容的交付物。
- 含姓名、学号、学习成绩、私人文件、私人截图、令牌、Cookie、API Key、订阅网址、数据库或其他敏感信息的文件，不得自动提交到公开仓库。
- 此类文件应使用用户确认的 **Private** 仓库或其他受控存储。尚未提供私人目标仓库时，只输出本次会话的文件，并说明尚未备份 GitHub。
- Private 仓库也不适合保存未加密密码和密钥，应用专门的密钥管理或加密存储。
- 对容量大、频繁变动的二进制文件，应优先评估 GitHub Release、Git LFS 或其他对象存储，避免令普通 Git 仓库膨胀。

## 路径示例

- `userscripts/chaoxing-question-export/chaoxing-question-export.user.js` — 脚本正式入口，后续始终更新同一路径。
- `network/clash-verge-rev/clash-verge-rev-extension.js` — 通用配置脚本正式入口。
- `apps/pdf-toolbox.html` — 单文件网页工具正式入口。
- 新的通用可公开产物可放 `artifacts/<project-slug>/<canonical-name>.<ext>`，保持稳定路径。

## ChatGPT 多对话注意

本规范对 GitHub 仓库本身有效，但无法自动成为 ChatGPT 账号的全局自定义指令。
若希望不同聊天也优先遵循，应在 ChatGPT **设置 → 个性化 → 自定义指令**添加一条简短的同等规则；此外具体会话必须具有 GitHub 连接、授权和实际上传能力。
